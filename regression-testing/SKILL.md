# 行为与回归测试

沿[软件工程原则](../docs/software-engineering-system.md)，从用户目标和独立业务事实写预期：用户需要理解什么、完成什么判断或操作、取得什么正确结果。不能把当前代码输出、现有UI或作者样例本身当正确答案。选择能捕捉目标缺陷的最小测试层，小改只核受影响保证，不为每个补丁重走业务或全矩阵。权限覆盖真实授权边界，数据一致性覆盖实际写入边界；使用隔离数据与项目已有工具，明确替身范围。

1. 对可复现缺陷和适合先写测试的关键行为，先在未修基线上运行定向测试。核对它是否因预期业务断言失败。测试未启动、样本无效或环境错误先单独处理。
2. 修改最小必要实现后，运行同一测试并读回结果。必要时补主路径与关键拒绝或恢复场景，运行受影响的现有测试。重构时用既有行为基线做前后比较。
3. 已有实现时，可在安全的隔离基线上验证同一断言能抓住旧行为。基线无法复现时，记录原因、当前检查的覆盖范围及尚缺证据。涉及有副作用的操作使用可控测试数据。
4. 在原记录保留测试位置或步骤、适用版本、输入和实际结果即可，不逐层重复写报告。优先断言任务结果和业务依据；错误提示、控件存在或请求成功断言不能代替正向结果。若已知核心用途缺失，明确功能仍不通过并续原修复，不能用新增通过用例抵销。避免把断言绑在可替换的内部实现上。

批处理、恢复或身份事实生命周期改变时，选择受影响的跨批事实更新/撤回及“业务已提交、控制确认丢失”场景。沿原键读持久结果、补正常确认，验证未重复写、旧记录与人工修改保留；业务提交数与控制确认数分列。I/O模型不冒实际提交或恢复通过。

复发时核原用例漏了哪一层真实构造、编码、提交或事实生命周期，修原代码和用例；不以增加审核轮次替代。已有用例能捕捉该回归时复用。低影响改动使用与影响相称的检查。

跨层装配或批处理变化时，fixture从真实producer导出派生，同一对象和上下文穿过被测caller、编码、consumer、提交与恢复边界；不得私添真实API没有的能力，或把被验证的逻辑换成返回预期值的替身。只替外部I/O并明示范围。涉及规模时检查关键调用和解析次数如何随输入增长；离线模型计数不能冒实际环境吞吐。未变层的有效证据直接复用，不据此新建整套演练。
