# 已观察的协调错误模式

以下是已有交付中实际出现、可用于识别相似问题的反例，不是每次必须跑完的检查清单。只读命中当前现象的条目；项目记录保留具体证据，通用技能不搬入业务数据或执行参数。

| 实际错误模式 | 已采用的纠正方式与适用边界 |
| --- | --- |
| 只检查固定批次，漏掉同期已授权补漏；局部完成被当作整目标完成 | 对照原完整目标和当前子集，保留未覆盖项的原负责人及下一节点；不另建目标台账。 |
| 负责人标记活跃或消息已送达，下阶段仍未开始 | 核对应阶段的实际产物、执行或结果；按原负责人直接接续，不能用 ACK 或协调记录自引用代证据。 |
| 所有任务笼统等公共服务或安装，独立源码准备也停工 | 追到具体接口、配置、对象及真实写冲突；只等待受影响动作，不假设所有项目都能并行。 |
| 安装时才发现启动入口、实际模块解析、响应入口注册、配置、客户端或初始化缺件 | 用现有[宿主就绪方法](../../implementation-planning/references/host-readiness.md)处理发生变化的实际运行组合，由原提供方交齐已知必需项；分别核请求来源、执行版本、授权起止与执行窗口，依赖、来源和期限不能相互冒用。复用同源证据，只补改变处，不作为每批固定新检查；不逐叶安装或把模拟通过称实际可用。 |
| 后继沿旧版本、旧状态或推测继续归因，真实命令类型或对象存在性与推测不同 | 先读回准确对象及实际作用范围，再更正原判断；保留旧历史，不扩大为所有数据的全盘扫描。 |
| 少量成功、健康检查或正常退出被报告为完整业务交付 | 按原交付目的区分源码、安装、数据/业务和接受；部分成果只关闭对应范围。 |
| 反复查询同一失败、重复唤醒，或为证明方法更新重跑旧业务 | 复用有效证据；有新事实才改动作，下一必要交付中观察效果，不另开方法验收流程。 |
| 清了缓存或写了清理策略，却未实际退役可恢复旧副本 | 按原[资源生命周期方法](../../project-mgmt/references/resource-lifecycle.md)核实际退役及保护例外；空间变化与逻辑目录大小分开，不由主调度越权删除。 |

这些反例证明相应问题确实发生过，不证明某种干预在所有项目都更快。判断方法是否有效，要看后继实际接续、有无误催或重复执行、请求结果是否交付。最新恢复算法、批量初始化实现、自动派单机制和未经独立确认的性能收益不在本参考推广。
