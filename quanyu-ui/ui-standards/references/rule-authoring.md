# 从问题到可执行规则

本页是编写方法和示例，不是一套预设主题。具体组件名、字号、断点、品牌和允许的业务操作从当前项目取。

## 一条规则应包含什么

| 内容 | 要回答的问题 | 避免 |
| --- | --- | --- |
| 问题与影响 | 用户在哪个任务中看不清、找不到或误操作？ | “页面不高级”“优化体验” |
| 适用与例外 | 哪类页面、状态、设备适用？什么情况下不适用？ | 一次表格问题扩大到所有页面 |
| 正确处理 | 哪个角色负责结构，哪个角色提供业务字段？ | 用视觉规则决定授权或业务结论 |
| 正反例 | 同一任务下差异是什么？ | 只有概念词或一张无法追溯的漂亮图 |
| 接入 | 现有组件、语义属性或组合方式是什么？ | 看似可复制但不存在的 API |
| 通过条件 | 实际观察什么结果？ | “已引用组件”“检查脚本通过”代替界面 |

规则写进当前项目已有规范；问题实例、源版本和证据写进任务记录，并相互引用。不强制为每条规则创建新文件。

## 示例一：分组标题与字段值混同

**问题：** 详情中“处理结果”与“已退回补充”采用相同字号、字重和间距，用户无法判断哪个是章节、哪个是真实状态。

**正确处理：** 为区块标题、字段标签、字段值、状态定义不同语义角色。层级综合使用字重、行高、分组距离与分隔，不只扩大字号。具体字族和尺度引用项目现有来源；状态仍用文字说明，颜色不是唯一通道。

**正例（结构示意，不是组件接口）：**

```text
处理结果                         ← 区块标题，采用项目标题角色
────────────────────────────
处理结论                        处理时间   ← 字段标签
退回补充                        09:30      ← 真实值，状态文字可辨

补充要求                                   ← 次级相关小节
请补充材料的有效日期。                     ← 正文，不能弱化成难读脚注
```

**反例：** 每一行都加粗；把重要补充要求缩成低对比小字；用蓝色大标题代替真实状态；不考虑主题/语言而固定所有主副文字同比例缩放。

**接入：** 优先使用项目已有标题、字段摘要和状态组件，调用者提供真实文案与标题级别。共享组件默认角色有误时修共享维护源；仅调用错角色则修调用。

**通过条件：** 在实际字体和长短内容下，能区分“这是分组”“这是字段”“这是状态/值”；窄屏换行后仍成立。不能靠 DOM 中有 heading 或截图存在判通过。

## 示例二：编辑区域不易发现

**问题：** 点击长列表后部的“编辑”，完整表单出现在整表底部，用户看不到反馈，也不知道正在编辑哪条。

**正确处理：** 按任务选承载：极短局部调整可内联，集中的短任务可用弹窗，需要保留列表背景的有限任务可用侧面板，长流程/附件/复杂对照可用独立工作面。组件是模态还是非模态按其实际契约决定，不为对照背景删除焦点或遮罩规则。字段数只是参考，不设万能阈值。

**正例：** 从某条记录打开既有编辑面，标题/摘要显示原对象；输入就近校验；继续编辑保留草稿并回到可见控件；明确放弃才清除；关闭后回原记录及条件。

**反例：** 一律搬进巨大弹窗；将同一表单放到列表末尾再自动滚到底；取消保护草稿但 Escape 静默丢弃；关闭后重置所有筛选。

**通过条件：** 从列表后部真实打开、取消、必要的脏值确认，再观察对象、输入、焦点与返回位置。纯承载改变不要求重放已通过且未变的写入/审批；缺合法样本的业务分支另列。

## 示例三：规范与任务记录分开

**规范正例：** “分页或钻取改变明细后，应让新明细的范围提示和起点可见；只聚焦一个超长容器可能让浏览器保留在底部。采用现有定位能力，核对实际视口和首条记录；不要滚到无关全页标题。”

**任务记录正例：** “候选 X，在目标窄视口切至第二页后首条位于视口上方；修复 Y 后范围及首条完整可见，原失败图保留。其余通过项复用。”

**反例：** 把本次日期、端口、记录 ID、修复提交、某个固定像素位置写入长期规范，要求所有项目都达到该像素或重跑此次操作。

## 自动检查的边界

对注册值、组件 API、清晰定义的结构做确定性检查。对视觉关系保存实际观察或配对证据。只有需要判定的新输入变化才使相关证据失效；规范修订不自动否定所有历史通过项。发现规则无法落地时，先修说明、示例或组件，不靠增加勾选项掩盖问题。
