# UI 规范维护

先读当前项目规则、现有设计规范索引及本次需求。项目的品牌、平台、组件契约、业务语义和责任分工仍由项目决定；本技能提供规范组织方法，不提供统一主题或额外操作权限。

## 复用权威来源

找到当前项目规范的维护入口、已确认设计和组件实现。使用项目已有的专属扩展；扩展可由项目规则指向一个普通文档或专属技能，不要求新注册表或固定文件名。没有扩展时，沿现有资料执行，只将影响任务的缺项列为设计假设；重要业务或方向不明才澄清，独立工作继续。

长期规则与任务记录分开：规范说明何时适用、为什么、怎么做及如何判断；本次对象、日期、失败图、修复提交、安装和待补样本留在原任务记录。规范中可保留必要的版本说明，不把某批通过或某个提交写成永久要求。

复用[设计语言](../ui-design/references/design-languages/index.md)时，规范记录项目采用的语言、Token/组件映射和允许的密度/材质适配。语言通用方法由插件维护，项目决定和本批证据留原项目；不将某项目选定的语言变成插件默认，不复制插件正文另建竞争源。

涉及导航规范时，可按项目规模选择[导航模式](../ui-design/references/navigation-patterns/index.md)，记录分组或空间/域/功能语义、真实目录来源及宽窄承载；不复制其他项目具体空间、授权规则或验收结论。

目录与模板库的共性问题可引用[目录工作面](../ui-design/references/catalog-workspaces.md)，将密度、说明权威与配置上下文纳入项目具体接入和实际观察；不复制本批业务名称、对象或通过结论。

## 从发现形成规则

先区分：已有规则未执行、规则本身有缺口、共享组件能力不足、单次业务个例。已有规则未执行时补接入示例或检查点，不再建同义标准；共性能力修在实际维护源，业务个例留领域。只有可跨多个场景解释和验证的问题才提升为规则。

写规则时读取 [规则编写示例](references/rule-authoring.md)。每条至少能回答：适用什么任务；错误造成什么后果；正确与错误例如何不同；用哪类现有能力接入；怎样实际观察通过；哪些业务含义不能擅改。代码示例须标明真实接口还是示意，不把示例字段、回调或数据当产品契约。

更新既有索引与最具体规范，引用数值和组件的唯一来源，不复制另一套 Token、API 默认值或竞争规范。保留项目有意采用的例外及原因，不把单次偏好扩成跨项目禁令。

已选视觉方向落地、共享基础推广或样例与产品差距明显时，按需用[实现质量控制](../ui-review/references/implementation-quality.md)核真实内容、角色接入、设计偏差与功能/视觉双结论；工具只拦可判定缺证，不代替实际视觉判断。

## 让要求可执行

把确定性检查接到项目已有入口：例如合法组件接口、已登记语义值、可访问名称或引用完整性。先确认检查真正对应规则，再增补必要的窄检查；不要创建笼统评分、全局 hook 或仅靠字符串出现判定视觉通过。

检查只能证明其覆盖的结构。字体实际加载、层级、裁切、浮层定位和反馈可见性仍需在实际界面观察。没有现成脚本时可按规则定向人工核对，不为维护一条规范另造审计系统。

## 交付

在原交付记录说明改了哪条规则、对应何种可复用问题、示例是否可用、受影响检查与未验证边界。规范文件已存在、已安装、平台可发现、实际使用是不同事实；不承诺保存文件会让其他会话热更新，也不为规范升级重跑未变化业务。
