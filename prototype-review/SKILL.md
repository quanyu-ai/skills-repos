# 原型交接前评审

原型完成一个可走通的业务切片后，在交给开发前主动发起复核。普通文案、样式等未改变任务、状态、权限或信息含义的修改，核对受影响画面和必要回归即可。

1. **固定评审对象。**记录原型版本或链接、需求来源、涉及角色与关键验收场景。可用已获授权的独立评审者时，给对方原始需求、原型和样本，由其自行判断，暂不提供作者的通过结论。单执行者先结束设计，再从零按需求重走一遍并标记为单人复核。
2. **实际走路径。**从角色可见入口操作主流程，再覆盖受影响的异常、拒绝、返回或恢复。检查关键状态和结果提示、是否误导下一步、是否暴露其他角色或企业的信息。涉及金额、权限、不可逆操作时，优先检查拒绝、重复触发和结果未知。按项目目标视口检查必要的键盘、焦点和可见性。对能确定的链接、控件和状态，优先复用浏览器或现有脚本检查。
3. **分开结论。**把每项发现落到需求、版本、角色、入口、操作、观察结果和证据。区分影响正确完成任务的阻塞问题、可后续修的建议、待业务决定，以及缺少入口或样本而未运行的场景。静态稿只评可观察内容，交互原型中的拒绝或模拟结果只证明原型表现。
4. **修订并复验。**AI 能按已明确规则修复的，修复后沿同一路径复验。业务负责人只确认会改变规则、范围或取舍的决定。交接时在原记录写清当前版本、复验结果和剩余事项。只暂缓受阻的开发切片，独立工作可以继续。

多角色或多端变更，重点补查以下接缝，并复用已有角色表和测试：

- **入口与操作。**同一对象区分可见、可读、可改；隐藏菜单不足以证明拒绝。用原型支持的深链或隔离脚本尝试越权进入与提交，读回对象未变化。对象范围还包括企业、站点或受托批次，不能只检查角色名称。此类模拟拒绝仍不证明服务端授权。
- **配置与消费。**对受目录约束的字段，核对谁维护、谁选用、初始选项从何而来，以及停用或待审时如何处理。抽查配置变更后的新业务与既有业务是否按已确认规则采用或保留原版本。
- **跨角色闭环。**沿同一对象从发起、审核或配置走到下一负责人的待办、处理入口和结果回显。例如“申请平台安排”之后应能由对应岗位报价并交回确认，不能只验证申请按钮。缺失的业务规则单列待决定，不由评审自行补定。

结论按实际走过的角色、对象范围和状态给出。新增岗位或责任变更后复核受影响的接缝；不因一个主流程通过而宣称全部角色可用，也不要求每次重跑全部组合。

需要交接记录样式时，使用[最小模板](templates/handoff.md)或项目现有记录。有自动触发需求时，可参考[接入检查](references/hook-integration.md)。评审和交接可由同一工作流直接执行。
