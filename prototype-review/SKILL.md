# 原型交接前评审

原型完成一个可走通的业务切片后，在交给开发前主动发起复核。普通文案、样式等未改变任务、状态、权限或信息含义的修改，核对受影响画面和必要回归即可。

沿[软件工程原则](../docs/software-engineering-system.md)，先判断方案能否解决目标角色的问题，再检查实现是否符合方案。预期来自原用户目标和业务事实，不能让原型、当前代码和作者说明互相证明正确。用户须能看懂事项、据必要信息作判断或操作、取得结果并找回；仅有入口、漂亮画面或完备控件不是业务方案成立。

1. **固定评审对象。**记录原型版本或链接、需求来源、涉及角色与关键验收场景。可用已获授权的独立评审者时，给对方原始需求、原型和样本，由其自行判断，暂不提供作者的通过结论。单执行者先结束设计，再从零按需求重走一遍并标记为单人复核。
2. **实际走任务。**从角色可见入口走到能解决问题的结果，检查决定前的内容、对象、范围、依据和下一步是否充分。例如总览要让用户判断状况并找到需关注对象，不能只放查询入口；办理要让用户据真实要求选择和提交，不能只验证按钮。再按变化检查必要的异常、拒绝、返回、恢复及目标视口键盘和可见性。涉及金额、权限、不可逆操作时，保留拒绝、重复触发和结果未知检查；错误提示正确不能替代正向任务。
3. **判断任务是否成立。**核心用途缺失、信息不足以决定或结果不能接续，明确该方案不通过并交原设计修订，不用局部可用或未签整体免责。在原记录用必要的版本、角色、操作和观察说明问题即可；建议、待业务决定与因缺样本未运行的项分别注明。静态稿只评可观察内容，交互原型中的拒绝或模拟结果只证明原型表现。
4. **修订并接续。**AI 能按已明确规则修复的，修复后核原失败任务及直接受影响部分，复用未变结果。业务负责人只确认会改变规则、范围或取舍的决定。原记录说明任务结果、当前版本和剩余问题即可交接，不固定要求另一位审阅人的ACK、原型PNG或完整模板字段。只暂缓确实依赖未决设计的切片，独立工作继续。

多角色或多端变更，重点补查以下接缝，并复用已有角色表和测试：

- **入口与操作。**同一对象区分可见、可读、可改；隐藏菜单不足以证明拒绝。用原型支持的深链或隔离脚本尝试越权进入与提交，读回对象未变化。对象范围还包括企业、站点或受托批次，不能只检查角色名称。此类模拟拒绝仍不证明服务端授权。
- **配置与消费。**对受目录约束的字段，核对谁维护、谁选用、初始选项从何而来，以及停用或待审时如何处理。抽查配置变更后的新业务与既有业务是否按已确认规则采用或保留原版本。
- **跨角色闭环。**沿同一对象从发起、审核或配置走到下一负责人的待办、处理入口和结果回显。例如“申请平台安排”之后应能由对应岗位报价并交回确认，不能只验证申请按钮。缺失的业务规则单列待决定，不由评审自行补定。

结论按实际走过的角色、对象范围和状态给出。新增岗位或责任变更后复核受影响的接缝；不因一个主流程通过而宣称全部角色可用，也不要求每次重跑全部组合。

遇到入口、角色、提示或后继动作含义不清时，以当前版本中的一个具体任务开展定向问答：角色想完成什么、现在能输入什么、看到什么结果、下一步由谁做。先实际走路径和查原决定，再把疑点、画面／操作证据及可行选择交原设计／业务负责人澄清。答案回写原需求／原型并复验受影响路径；不能用讨论同意代替实际可用，也不要求所有普通评审逐项提问。只挂真正受影响切片，已确认决定不重复求批。

需要交接记录样式时，使用[最小模板](templates/handoff.md)或项目现有记录。有自动触发需求时，可参考[接入检查](references/hook-integration.md)。评审和交接可由同一工作流直接执行。
